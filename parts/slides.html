{{CHROME:02 · The solution · Search}}

Language picks the index.
Store becomes a filter.

Shopper contextlang = esstore = ST-ES-MAD-01
Index per languagehavenmart-essearches name_es, description_es
IQL filteravailability == "ST-ES-MAD-01"== on an array means “contains”
Resultranked, faceted, in stock
GET /search/v2/indices/{index_es}/query?query=leche&clientUUID={uuid}
    &filters=availability == "ST-ES-MAD-01"&facets=brand&token={trackerKey}
10 search indices per workspace · a brand-country with two languages uses two {{N}} / {{TOTAL}}
{{CHROME:02 · The solution · Recommendations}}

One campaign per model.
Language and store travel with the request.

Model

Campaign id — similar items, bought together, personalized. One each, for every language.

Language

displayAttribute=name_es — the response carries the shopper’s language.

Store

additionalFilters — the same availability clause, joined with AND to the campaign’s own filters.

GET /recommendations/v2/recommend/campaigns/{campaignId}?clientUUID={uuid}&itemId=HM-GRO-0116
    &displayAttribute=name_es&additionalFilters=availability == "ST-ES-MAD-01"&filtersJoiner=AND&token={trackerKey}
One campaign per model, not per language · displayAttribute does the translation {{N}} / {{TOTAL}}
{{CHROME:02 · The solution · Front end}}

The storefront calls Synerise directly.

  • Tracking code in the page. The SDK gives every visitor a profile UUID.
  • Tracker key on every call. Public by design: it reads search and recommendations, never configuration.
  • Events close the loop. Search clicks and recommendation views train ranking.
  • No API key in the browser. Index and campaign setup stays server-side.
This deck is the storefront: the same tracking code runs in it {{N}} / {{TOTAL}}
